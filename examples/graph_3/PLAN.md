## 1. Задача

Лес деревьев («граф рукопожатий»): люди, симметричные знакомства, несколько компонент
связности, каждая компонента — дерево ⇒ путь между любыми связанными людьми
**единственный**. Модель учится отвечать, через сколько рукопожатий знакомы X и Y
(1–8 хопов) или что они не связаны. Исследуем accuracy в зависимости от числа хопов
и глубину обобщения (train ≤ 6 хопов, test 7–8).

Чем постановка лучше graph_2:
- открытый ответ-число вместо Yes/No → нет 50%-floor и Yes-bias (см. graph_2 REPORT §2);
- путь единственный → и число, и цепочка проверяются детерминированно, без LLM-судьи;
- один формат вопроса в train и test (в graph_2 был рассогласован);
- сжатие ×5 закладывается в дизайн (в graph_2 было 1.22×).

## 2. Датасет

### Граф
- Лес из нескольких компонент (ориентир: 6–10 компонент по 30–60 человек; финальные
  числа — после статистики пар по хопам, см. §6 «Сжатие»).
- Каждая компонента — случайное дерево; валидация генератора: на каждый хоп n=1…8
  достаточно пар (примерно равные бакеты), иначе пересэмпл seed/параметров.
- Имена: уникальные реальные имена (связи случайны под seed — из претрейна не выучить).
- Корпус: по предложению на ребро, каждое ребро один раз:
  `Alice and Bob know each other.` (~8 токенов/ребро).

### Вопросы — один шаблон везде (train и test)
```
How many handshakes apart are {X} and {Y}?
If they are not connected, say so.
End your reply with "path: {X} - ... - {Y}" and "Answer: <number>",
or "Answer: not connected".
```

### Сплиты
| | хопы | негативы (разные компоненты) | баланс |
|---|---|---|---|
| **train** | 1–6, примерно поровну | ~10–15% | свободная генерация модели (self-study) |
| **test** | 1–8, поровну (7–8 — чистое обобщение) | отдельный бакет `none` | gold: число + единственный путь |

Негативы в train обязательны: в graph_2 их отсутствие в синтезе Exp 1 породило
Yes-bias — главную регрессию (REPORT §2, none-бакет 63% против 81.5% у ICL).

## 3. Scratchpad (формат рассуждения в подсказке Exp 1)

Выбран **push/pop лог на очереди** (BFS-вариант заметки Alex; стек из его примера —
это DFS, который порядок обхода даёт, а дистанцию — нет). Элементы несут дистанцию,
иначе из лога не извлекается число хопов:

```
queue: [Alice(0)]
pop Alice(0) -> visit, push Bob(1), Carol(1) -> queue: [Bob(1), Carol(1)]
pop Bob(1) -> visit, push Dave(2) -> queue: [Carol(1), Dave(2)]
pop Carol(1) -> visit, push Eve(2) -> queue: [Dave(2), Eve(2)]
pop Dave(2) -> visit -> queue: [Eve(2)]
pop Eve(2) -> visit, push Grace(3) -> queue: [Grace(3)]
pop Grace(3) -> target found at distance 3
path: Alice - Carol - Eve - Grace
Answer: 3
```

Негативы — фронтир исчерпан:
```
...
queue: []  -> frontier exhausted, Grace not reached
Answer: not connected
```

Генерируется детерминированно из графа (модуль `graph_index.py`). Каждая строка
программно проверяема. Длина ≈ строка на человека компоненты — поэтому компоненты
держим по 30–60 человек (см. SCRATCHPAD_FORMAT.md про цену длинных трейсов).

**Thinking-режим Qwen3: ВКЛЮЧЁН** (решение 11.06 после ночного прогона). Первая
итерация шла без thinking — ICL-бейзлайн рухнул до 12.1%: модель не ищет по графу,
а отвечает «not connected» на 96% вопросов (см. результаты ниже). Без thinking
Qwen3-1.7B не запускает поиск вообще, исследовать «рассуждения» нечем. Все три
команды (`run_exp0_icl.sh`, `run_exp1_synth.sh`, `run_exp2_synth.sh`) теперь идут
с `--thinking` по умолчанию (`THINKING=0` выключает). Парсер всегда читает зону
после `</think>`, обрезанные мысли ловятся как unparsed + `--rerun-unparsed`.

## 4. Эксперименты

| | Что | Данные обучения |
|---|---|---|
| **Exp 0** | ICL baseline | — (граф в контексте, accuracy vs hops) |
| **Exp 1** | adaptive hint self-study | Для каждого train-вопроса: модель отвечает с графом в контексте **без подсказки**. Верно → трейс в датасет. Неверно → регенерация с контекстом «граф + scratchpad-ответ» (по правке Alex от 09.06 13:39) |
| **Exp 2** | plain self-study | вопрос + граф → ответ модели, **все** трейсы без фильтра |
| **Exp 3** | rejection sampling | как Exp 2, но трейсы с неверным ответом отсеяны (`correct=True`) |

Exp 3 реализован как чистый фильтр поверх Exp 2 — `synthesis/exp3_build.py`,
без перезапуска сервера (метаданные `correct` уже в exp2-датасете). На текущем
лесу фильтр оставляет 261/2045 трейсов, причём хопы 4–6 пустые (0 верных) —
ожидаемый коллапс rejection sampling на сложных примерах (ср. graph_2 REPORT §3).

Все картриджи: KL-дистилляция логитов в замороженный Qwen3-1.7B, init `KVFromText`,
как в graph_2 (lineage_train.py почти не меняется).

## 5. Эвал и метрики

Генерация eval:
- длина eval - достаточно большая для конца генерации ответа

Парсинг (детерминированный, без LLM-судьи):
- `extract_answer(text)` → int | "not connected" | None — последняя строка `Answer:` в зоне ответа;
- `extract_path(text)` → list[str] | None — последняя строка `path:`.

Метрики:
- **acc** (primary) — exact match числа / not connected; разбивка по хопам 1–8 + `none`;
  отдельно хопы 7–8 = глубина обобщения;
- **fidelity** (secondary) — число верно **И** путь совпал с единственным gold-путём
  (ловит «угадал число»; ср. arXiv:2408.09529);
- **MAE** — |pred − true| на ошибках (насколько промахивается);
- unparsed-rate — доля None (как в graph_2 analyze).

## 6. Сжатие ×5 (порядок действий — важно)

1. Сгенерировать лес, добиться достаточного числа пар на каждый хоп 1–8 (равные бакеты не менее 100-120 вопросов).
2. Измерить корпус в токенах токенизатором Qwen3.
3. `CARTRIDGE_TOKENS = len(corpus_tokens) / 5`.

(Не наоборот: размер картриджа подгоняется под граф, а не граф под картридж.)

## 9. Открытые вопросы / риски

- Финальные размеры графа — после статистики §6 (Igor пришлёт ориентир по людям).
- Push/pop лог при компонентах >60 человек разрастается (>1k токенов на пример) —
  если упрёмся, fallback: level-frontier формат (см. SCRATCHPAD_FORMAT.md, вариант 1).
- Length-генерализация на хопы 7–8 может не появиться (CLRS-Text: «barely extrapolate») —
  это валидный результат, а не баг постановки.
- В Exp 1 подсказка содержит готовый ответ → трейсы-с-подсказкой могут быть
  «переписыванием» — честно репортить долю adaptive-регенераций по хопам
  (аналог star_survival.json).
